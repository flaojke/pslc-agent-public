# operator-workspace Specification

## Purpose
Предоставляет сотруднику ИТ единое рабочее окно для устройств, задач, событий и знаний с явным состоянием доступа и подключений.

## Requirements

### Requirement: OW-001 Authenticated local workspace
Система SHALL после аутентификации предоставлять «Основной раздел», «Устройства», «События», «Знания» и «Планировщик»; настройки доступны отдельно. Default SHALL использовать локальные УЗ; admin управляет сотрудниками, AD/SSO отложен. Legacy-local/OIDC требуют явного выбора без fallback. Режим разработки и неполнота внешней приёмки MUST быть видны.

#### Scenario: Missing credentials
- **WHEN** запрос к операторскому API не содержит действующий токен
- **THEN** возвращается 401 без данных устройств/задач

#### Scenario: Workspace navigation
- **WHEN** оператор вошёл в локальный стенд
- **THEN** доступны пять рабочих разделов, отображаются реальные списки и состояние интеграций без демонстрационных устройств под видом реальных

#### Scenario: Organizational login
- **WHEN** выбран режим OIDC
- **THEN** UI предлагает организационный вход, локальный операторский токен не принимается

### Requirement: OW-002 Honest integrations
Система SHALL вызывать только явно настроенные endpoints модели и read-only Confluence. Без конфигурации MUST возвращаться not_configured без выдуманного LLM ответа или внешнего fallback. Модельные обращения/ответы MUST оставаться временными; явно сохранённый schedule template допускается только по TR-004.

#### Scenario: Unconfigured model
- **WHEN** оператор отправляет вопрос без настроенного model endpoint
- **THEN** интерфейс сообщает, что модель не подключена, и не выдаёт шаблонный ответ за ответ LLM

#### Scenario: Configured knowledge search
- **WHEN** настроен Confluence и оператор ищет знания
- **THEN** выполняется запрос только в разрешённых пространствах с ограниченным ответом и ссылкой на источник, без записи страниц

### Requirement: OW-003 Primary agent prompt
После входа система SHALL открывать «Основной раздел» с одним окном задания агенту, уточнением, планом, подтверждением, исполнением и проверенным итогом в той же области. Точные формы устройства SHALL оставаться дополнительным способом работы; они не заменяют основной поток и не обходят его подтверждение.

#### Scenario: Default entry
- **WHEN** оператор вошёл или выбрал «Основной раздел»
- **THEN** видит одно поле промптинга агенту; каталог и командные формы не занимают главный экран

#### Scenario: Installation context
- **WHEN** оператор открывает устройство
- **THEN** может подготовить и подтвердить установку в его контексте и вернуться в основной раздел

#### Scenario: Main action lifecycle
- **WHEN** оператор отправил допустимое задание из основного окна
- **THEN** может просмотреть и подтвердить план, наблюдать исполнение и проверку без перехода к устройствам

### Requirement: OW-004 Case dialogue design
Интерфейс SHALL применять выбранный1C и проверяемыеUX-01–36: светлая иерархия, один ввод над диалогом, ясные этапы/цели/модель. Пять рабочих разделов, включая отдельный «Планировщик», SHALL сохранять главный разговор по умолчанию. Вторичные формы не конкурируют с ним.

#### Scenario: Main navigation
- **WHEN** сотрудник входит и создаёт беседу
- **THEN** открывается разговор с этапами разбора; устройства/события/знания доступны отдельными понятными переходами

### Requirement: OW-005 Accessible interaction
Основные потоки SHALL быть доступны с клавиатуры, иметь видимый неперекрытый фокус/подписи, текстовые статусы, контраст4.5:1 обычного текста и применимые критерииWCAG2.2AA. UI SHALL перестраиваться на320CSSpx и при200%текста; таблицы прокручиваются отдельно.
#### Scenario: Narrow keyboard flow
- **WHEN** оператор проходит беседы/выбор целей/план без мыши на узкой ширине
- **THEN** функции не теряются, фокус не прячется, сообщение и подтверждение не срабатывают одним сочетанием

### Requirement: OW-007 Settings beside the main workspace
Основные устройства/диалог/события/знания SHALL сохраняться; вторичные модели/УЗ/руководства SHALL открываться из «Настроек» с понятной вложенной навигацией, клавиатурой и reflow. Возврат MUST сохранять выбор беседы/серверный временный контекст и не запускать задачи.
#### Scenario: Read a guide and return
- **WHEN** оператор уходит из чата в руководство и обратно
- **THEN** продолжает выбранную беседу в рамках её TTL, а просмотр не запускает установку/команду/сканирование

### Requirement: OW-006 Review and restore in case flow
Интерфейс1C SHALL показывать пару forward/anti-script, declared coverage/срок/исход snapshot, кнопку «Откатить задачу» для шага/группы и отдельный exact rollback plan. Истёкшие имена/содержимое MUST не выдумываться: показываются frozen IDs/hash/type counts. Результаты SHALL различать restored/partial/conflict/unavailable и историческое постусловие.
#### Scenario: Restore failed action
- **WHEN** forward завершился ошибкой после snapshot
- **THEN** владелец может отдельно подготовить и подтвердить доступный rollback, а running/unknown требует сверки
#### Scenario: No mutation
- **WHEN** шаг health/investigate либо forward не начинался
- **THEN** UI объясняет отсутствие необходимости отката без ложной кнопки универсального восстановления
