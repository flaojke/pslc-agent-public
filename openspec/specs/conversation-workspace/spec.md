# conversation-workspace Specification

## Purpose
Обеспечивает отдельные приватные беседы оператора с агентом и продолжаемый разбор инцидента, сохраняя полный контекст только в ограниченной временной памяти.

## Requirements

### Requirement: CW-001 Owned conversation lifecycle
Система SHALL позволять создавать, переименовывать, выбирать и удалять собственные беседы с коротким явным названием. Чужие диалоги и контекст MUST не раскрываться. Удаление SHALL скрывать беседу, не удаляя обязательные метаданные выполненных задач. Пока выбранная беседа не загружена, UI SHALL блокировать сообщение/план в прежнюю беседу, сохраняя ввод черновика и создание при пустом выборе.
#### Scenario: Separate cases
- **WHEN** сотрудник ведёт беседы о доступности и ПК-128
- **THEN** сообщение и план одной беседы не получают контекст другой; другой сотрудник не открывает их по ID
#### Scenario: Delete with live work
- **WHEN** удаляется беседа с активными заданиями
- **THEN** требуется явное решение запросить отмену; UI не объявляет уже начавшийся процесс отменённым или откатанным
#### Scenario: Selected conversation is still loading
- **WHEN** оператор выбрал другую беседу, её GET ещё не завершён и оператор вводит сообщение либо пытается подготовить план
- **THEN** сообщение и план не отправляются в предыдущую беседу; после загрузки операции привязаны к новому выбранному ID
#### Scenario: Actor changes before creation or send completes
- **WHEN** создание беседы либо отправка завершается после unmount/смены сотрудника
- **THEN** поздние create/POST MUST не менять выбор/черновик другого сотрудника или беседы

### Requirement: CW-002 Bounded temporary dialogue
Полный диалог SHALL находиться только в RAM: до40сообщений/64KiB на беседу, TTL30минут, ограничение общего числа контекстов. В истории SHALL оставаться только краткое имя, ID, время, тип/исход и ссылки задач. Истечение контекста MUST показываться явно.
#### Scenario: Reload and expiry
- **WHEN** страницу обновляют до TTL либо сервер перезапускают
- **THEN** до TTL владелец видит временный диалог, после потери RAM — только метаданные и сообщение о необходимости восстановить контекст
#### Scenario: Source marker
- **WHEN** уникальная строка есть в вопросе, ответе или исходном выводе
- **THEN** она отсутствует в БД/очереди/backup/telemetry и браузерном постоянном хранилище

### Requirement: CW-003 Observable dialogue generation
Отправка сообщения SHALL продолжать беседу с доступной моделью, показывая очередь/обработку/ошибку и позволяя отменить ответ. Нет модели — нет имитации её ответа. Отмена MUST отбрасывать поздний ответ без обещания мгновенно остановить вычисление.
#### Scenario: Follow up
- **WHEN** пользователь уточняет ранее описанную проблему
- **THEN** модель получает допустимый контекст этой беседы; ни сообщение, ни ответ не запускают узловую команду
#### Scenario: Cancel response
- **WHEN** ответ отменён до завершения модели
- **THEN** поздний результат не появляется в беседе и ничего не исполняет

### Requirement: CW-004 Explicit contextual action
Из беседы SHALL быть возможно отдельно подготовить точный план с выбранными целями и связать его с разбором. Подготовка/просмотр MUST не исполнять шаг. Уточнение после плана SHALL создавать новый план, не меняя подтверждённый.
#### Scenario: Clarified plan
- **WHEN** после уточнения пользователь готовит действие
- **THEN** используется текущий ограниченный контекст и новый снимок целей; требуется новое подтверждение

### Requirement: CW-005 Selected case interface
Главный интерфейс SHALL следовать1C: один ввод над диалогом, отдельный список бесед, явные цели/модель, хронологические этапы «Уточнение/Факты/План/Проверка» и краткий текущий итог. Доступность SHALL проверяться в реальном UI, не по PNG.
#### Scenario: Resume case
- **WHEN** оператор возвращается к разбору
- **THEN** видит фазу/метаданные и последнее требуемое решение, может продолжить ввод без перехода в форму устройства

### Requirement: CW-006 Compact historical messages
Длинное старое текстовое сообщение SHALL по умолчанию показывать первую непустую строку с многоточием и доступным «Развернуть/Свернуть». Последнее текстовое сообщение MUST оставаться открытым. Короткие сообщения, планы и решения MUST не скрываться. Ручное раскрытие SHALL сохраняться только в RAM и не менять полный текст/retention.
#### Scenario: Previous large answer
- **WHEN** после длинного ответа появился следующий вопрос/ответ
- **THEN** прежний ответ по умолчанию компактен, последний текст полностью виден
#### Scenario: Pending long question
- **WHEN** длинный вопрос ещё ожидает ответа
- **THEN** он полностью открыт, после ответа может стать компактным историческим сообщением
#### Scenario: Keyboard expansion
- **WHEN** оператор раскрывает старое сообщение клавиатурой
- **THEN** видит полный доступный текст, может свернуть обратно; новый ответ не отменяет его ручной выбор
