# Инструкция администратора PSLC Agent

Версия приложения: 0.18.1. Для владельца контура и сопровождения.

Источник: docs/product-guides.json. Файл генерируется; изменяйте исходник и запускайте scripts/generate_product_guides.py.

## Назначение и границы MVP

PSLC Agent — система поддержки и администрирования Windows/Linux: сотрудник описывает проблему, модель помогает её разобрать, отдельный план после подтверждения выполняется узловым агентом и проверяется по постусловию. Версия 0.18.1, схема метаданных 9, native агент 0.8.0.

- До 500 зарегистрированных устройств. До 5 активных шагов в сеансе и до 20 удалённых заданий на весь парк. Эти лимиты не умножаются на число машин.
- Основной раздел — беседы, единое поле ввода, явный выбор машин и ход разбора. Устройства — реестр, подключение и настройки. События — метаданные исполнения. Знания — отдельный контур с контролем доступа.
- Роли: Оператор ИТ, Аудитор ИБ, Ревью знаний, Администратор платформы. AD/SSO и Confluence не входят в текущий набор подключений.
- Ручной откат восстанавливает только объявленные ресурсы по локальному baseline с отдельным подтверждением. Планировщик находится в следующем OpenSpec-срезе. Отмена запроса не является откатом.

> Ответ модели и обнаруженная по сети машина не являются проверенным фактом или управляемым узлом. Демо-устройство — симуляция health без выполнения команд на компьютере пользователя.

## Роли, области устройств и учётные записи

Роли комбинируются. Область устройств задаётся отдельно: «все» либо конкретные IDs. Роль администратора на одном устройстве не даёт право менять глобальные модели/систему/сотрудников. Для глобального администрирования нужны одновременно platform_admin и scope *.

| Подключение и переключение LLM | Нет | Нет | Нет | Глобальная область |

1. Настройки → Доступ и роли: изучите матрицу и эффективные права текущего пользователя. В accounts-режиме любой сотрудник может сменить собственный пароль с проверкой текущего.
2. Глобальный администратор создаёт сотрудника, выбирает готовый профиль роли либо комбинацию и явно задаёт устройства. Профиль не назначает все устройства скрыто. Новый пароль не менее 8 символов.
3. Для оператора назначьте нужные устройства. Для аудитора доступны метаданные и события этих устройств без чужого временного диалога/кода/output. Для ревьюера дополнительно нужны пространство/ACL и доступный коннектор знаний.
4. После изменения прав/пароля/disable прежняя сессия инвалидируется. Повторный вход читает актуальные grants. Последнего включённого глобального администратора нельзя отключить, лишить роли или глобальной области.

> Матрица показывает ролевой допуск, но не отменяет owner boundary, device scope, space ACL, доступность коннектора, opt-in узла и точное подтверждение. AD/Confluence пока отложены. Не выдавайте reviewer за работающую публикацию при отключённом коннекторе.

## Подключение узлового агента Windows/Linux

1. В Устройства → Подключить устройство задайте имя профиля, ОС, тип «Пользовательская машина»/«Сервер»/«Не определён» и необходимые возможности. Для первой проверки оставьте команды, установки и диагностику выключенными. ОС и тип — разные признаки.
2. Создайте профиль. Одноразовый код действует 10 минут; передайте его установщику защищённо. Код не включён в ZIP и не является постоянным operator token.
3. Скачайте полный архив агента для выбранной ОС. В него входят native runtime, config, SHA256SUMS, verifier, лицензии и шаблоны служб. Python на узле не нужен. Защищённый download handle действует 10 минут; при истечении/использовании создайте новый профиль.
4. Сверьте архив/manifest и распакуйте под выбранной identity. Проверьте server, CA, абсолютный путь state, локальные opt-in. Для удалённого узла HTTPS server должен быть доступен из его сети.
5. Запустите --enroll --once в терминале, введите код в скрытый запрос. Проверьте появление узла, тип и health. Затем запустите постоянно foreground или настройте службу отдельно.
6. Сохраните identity/state и права. Не копируйте identity на другую машину, не удаляйте её для «переподключения»: это постоянная уникальная credential. Отзыв credential/переподключение выполняйте через явный административный процесс.

```powershell
.\verify.ps1
.\native\pslc-agent.exe --config .\config.json --enroll --once
.\native\pslc-agent.exe --config .\config.json
```

```sh
sha256sum --strict --check SHA256SUMS
chmod +x native/pslc-agent
./native/pslc-agent --config "$PWD/config.json" --enroll --once
./native/pslc-agent --config "$PWD/config.json"
```

> Если state уже существует, enrollment откажет и сохранит identity. Не исправляйте это удалением файла. Проверьте, что запускаете нужный config и ту же identity. CA не отключайте при TLS-ошибке.

Серверная возможность и локальный opt-in должны совпасть. Включение флага только в интерфейсе не даёт агенту дополнительных прав ОС. Health собирает только краткие метрики, диагностика использует отдельные фиксированные ограниченные сборщики. Установка использует утверждённый каталог; произвольный URL модели не исполняется.

## Постоянная работа агента и права службы

Сначала подтвердите foreground enrollment и health. Архив ничего не устанавливает и не запускает как службу автоматически. Примеры путей ниже — шаблон, их нужно сопоставить с вашим развёртыванием. Не выдавайте доступ на запись к runtime/исполняемым файлам сервисной identity.

### Windows SCM

- Поместите native runtime в C:\Program Files\PSLC-Agent\native; администраторы управляют файлами, сервисная identity читает/исполняет.
- Config: C:\ProgramData\PSLC-Agent\agent-config.json. State: C:\ProgramData\PSLC-Agent\state\identity.json. В config укажите абсолютные пути. Config/CA читаются службой; только каталог state доступен ей на изменение.
- Шаблон deploy/install-windows-service.ps1 из source либо deploy/ архива создаёт службу от LocalService в остановленном состоянии. Проверьте его параметры -AgentExe, установите по принятой политике, затем Start-Service PSLCAgent.
- Enrollment выполняйте под той же identity и с тем же state. Foreground от администратора и SCM LocalService имеют разные права. Подготовку identity/config ACL и enrollment процесса службы согласуйте с администратором; не передавайте всем доступ к credential.
- LocalService не является администратором. Установка ПО/изменение системных ресурсов потребуют отдельного решения о сервисной identity, разрешениях и возможностях; health-only не доказывает эти операции.

### Linux systemd

- Создайте отдельного непривилегированного пользователя pslc-agent. Runtime root-owned в /opt/pslc-agent, без права записи для агента.
- Config /etc/pslc-agent/agent-config.json — root-owned 0640, читается группой агента; CA тоже read-only. State /var/lib/pslc-agent — владелец pslc-agent,0700; identity0600. В config задайте эти абсолютные пути.
- Выполните enrollment под сервисным пользователем с --config /etc/pslc-agent/agent-config.json --enroll --once; код вводится в скрытый интерактивный запрос.
- Адаптируйте deploy/pslc-agent.service (ExecStart/User/WorkingDirectory/ReadWritePaths), установите unit по политике хоста; systemctl daemon-reload и systemctl enable --now pslc-agent после проверки.
- Шаблон с NoNewPrivileges и ProtectSystem=strict подходит для минимальных возможностей. Он не обещает произвольный apt/dnf install. Привилегированные операции требуют отдельной настройки, ИТ/ИБ и тестового узла.

> Native health проверен на Windows и в изолированном Linux-контейнере/WSL2. Фактическая установка вашей SCM/systemd-службы, корпоративная подпись и реальные удалённые узлы остаются отдельной приёмкой.

## Подключение LLM: локальная модель и OpenWebUI

Настройки → Модели — единое место настройки. Профили, защита API key, выбор модели и тест подключения сохранены из прежнего раздела. Глобальный администратор с областью «все устройства» управляет подключением; остальные видят сведения и инструкцию. При открытии справки или About никаких сетевых тестов и скачиваний не происходит.

### Локальный CPU

1. По умолчанию выбрана Qwen3.5-4B Q4_K_M; GPU не требуется. Проверьте статус файла и runtime в Моделях. Full содержит проверенные веса, Lite позволяет скачать их кнопкой внутри приложения после развёртывания.
2. Нажмите «Скачать» только если модель отсутствует, дождитесь окончания SHA256-проверки. Частичный/повреждённый файл не активируется. При ошибке сети повторяйте download, не переименовывайте временный файл в готовый.
3. Выберите доступную локальную модель, активируйте профиль и выполните тест. Для другой модели используйте поддержанный каталог/профиль; не подменяйте файл с ожидаемым hash.
4. Запросите короткую диагностическую консультацию. Реальный результат модели — гипотеза до проверки на устройстве; CPU-задержка зависит от процессора, контекста и параллельной нагрузки.

Локальный runtime использует CPU, контекст 8192 и ограниченную очередь; одновременно выполняется одна генерация. 5 шагов сеанса/20 удалённых jobs не означают 20 параллельных генераций. Встроенный меньший кандидат Qwen3.5-2B скачивается отдельно. Full содержит проверенные веса, Lite скачивает их по кнопке. Linux требует совместимых системных библиотек; см. развёртывание.

### OpenWebUI для ИИ-специалиста

1. Получите HTTPS base URL вашего OpenWebUI, API key именно с нужными API-правами, допустимые model IDs и доверенную CA. Одного ключа без адреса недостаточно. Для Qwen/Gemma используйте фактические IDs экземпляра, а не выдуманное имя.
2. В Настройки → Модели выберите внешний профиль, введите URL и ключ в защищённое поле. Нажмите «Загрузить модели», выберите ID из полученного списка.
3. Нажмите «Проверить подключение». Проверяется аутентификация/модель и ограниченный JSON-контракт. Если TLS/401/403/404/timeout — используйте раздел устранения ошибок; не отключайте проверку сертификата.
4. Сохраните подключение и активируйте нужный профиль. Для смены локальной/внешней модели используйте выбор профиля; прежний ключ не переносится незаметно на изменённый адрес.
5. Проверьте отдельные сценарии: консультация, корректный typed plan, отказ на неизвестной машине, явное подтверждение и проверка результата. JSON-test не заменяет оценку качества и безопасности.

- Ключ хранится server-local: Windows DPAPI identity, POSIX AES-GCM/master key с защищёнными правами. БД/metadata backup/source ZIP ключ не содержат. На другой сервер/identity введите его заново.
- Не передавайте ключ в чат, URL, скриншоты, переменные браузерного хранилища или репозиторий. Ревизия профиля защищает от перезаписи устаревшей формой; при конфликте перечитайте настройки.
- Инструменты провайдера отключены; команды выполняет наш агент по принятому плану. Ответ LLM, логи и содержимое Confluence рассматриваются как недоверенные данные.
- Для своего OpenWebUI отдельно проверьте доступность, разрешённые model IDs и качество ответов. Успешный probe не заменяет приёмку выбранной модели.

- [Официальная документация OpenWebUI API](https://docs.openwebui.com/reference/api-endpoints/)

## Данные, приватность и сроки хранения

| Данные | Где и как |
| --- | --- |
| Исходные логи, полный stdout/stderr, разовый код, свободные вопросы/ответы LLM | Ограниченная RAM, не БД/телеметрия/backup; явно сохранённый шаблон расписания — отдельное исключение ниже. |
| Диалог | TTL30 минут, до40 сообщений/64КиБ на беседу; детальный список последних turns ограничен, усечение обозначается. |
| Названия бесед, задачи, типизированные краткие исходы, события, статистика подтверждений/вопросов | Метаданные в SQLite/PostgreSQL. Названия без чувствительного содержимого. |
| Пароли сотрудников и credentials узлов | Проверочные хеши, не открытые пароли/credential. |
| API key LLM, настройки подключения | Защищённый локальный secret store; не portable metadata backup. |
| Метка контура, контакт поддержки, часовой пояс | Защищённый .local/system/preferences.json, отдельная config-копия. |
| Typed анти-программа, receipt и hash | Строгие metadata в SQL без путей/содержимого/forward кода. |
| Узловой baseline объявленных ресурсов | Зашифрован только на узле, до7 дней/100 снимков/1ГиБ; не server metadata backup. |
| Явно сохранённый prompt/script/postcheck/resources расписания | Отдельный encrypted server-local vault .local/schedules. Не SQL/telemetry/metadata backup/release. |

> ОС может использовать pagefile/dumps, провайдер LLM — собственное хранение. Это отдельные вопросы приёмки ИБ; приложение не обещает управление всеми внешними копиями. Не вставляйте реальные исходные логи в имена бесед, знания или документы.

Смена display timezone меняет только вид дат в интерфейсе. Временные метки, leases, TTL и процессы API остаются UTC. Настройка не запускает задания и не меняет расписания.

## Резервирование, восстановление и обновление

До обновления дождитесь/сверьте активные задания, остановите API и сохраните прежний код. Не удаляйте .local, accounts, identity/state агентов, сертификаты, каталог или model profiles. Для запуска используйте ту же сервисную identity.

```powershell
.\.venv\Scripts\python.exe -m backend.operations backup --output <новый-защищённый-путь>
```

Metadata backup содержит хеши паролей/credential и нуждается в защищённом хранении. Он не включает исходные логи, код, полный вывод, raw-диалог, TLS/LLM secrets или preferences. Отдельно сохраните .local/system/preferences.json, config/CA/trust и secret-management по принятому процессу. Секрет Windows DPAPI не переносим на другую identity; ключ LLM там вводится заново.

```text
python -m backend.operations restore --input <snapshot> --expected-digest <доверенный-SHA256>
```

1. Восстанавливайте только в НОВУЮ пустую целевую БД при остановленном API. Инструмент откажет перезаписывать существующую. SHA256 сверяйте по доверенному каналу; hash не заменяет шифрование или подпись.
2. После restore проверьте УЗ/узлы/credentials. Ранее running/cancel_requested/unknown становятся unknown с недействительной старой lease; никакие команды автоматически не повторяются.
3. При обновлении проверьте новый архив, замените код/web/зависимости и принятые version/config artifacts, сохранив рабочую .local, .env, secrets и узловые конфигурации. Установите requirements.lock.txt в прежнем venv.
4. Запустите один API process. Проверьте версию/схему, вход, права, модели, парк и подтверждённую health-only проверку. Не считайте наличие файла доказательством рабочего обновления.
5. Откат версии кода выполняйте только с совместимой схемой или копией БД до миграции. Сверьте неизвестные эффекты на узлах до новых действий. Restore drill на выбранной среде нужен отдельно.

Рекомендуемые начальные цели backup RPO≤24ч/RTO≤4ч — ориентир, не обещанный SLA. Само приложение не создаёт корпоративное backup-расписание. Один API process и RAM-контекст пока исключают HA.

## Скрипт, анти-скрипт и ручной откат

Каждая изменяющая команда имеет forward, обязательную постпроверку и recovery.resources. Сервер до подтверждения создаёт исполняемый restore-baseline-v1, привязанный к исходной задаче/узлу/набору ресурсов. Команда без такого контракта не выдаётся. Health/investigate — фиксированное чтение, откат им не нужен.

1. В плане проверьте основной скрипт, постпроверку, объекты восстановления и анти-скрипт. Для ручной команды в форме устройства задайте эти поля явно. В свободном диалоге модель должна запросить недостающие ресурсы, а не выдумать охват.
2. Узел protocol1/native0.8+ проверяет локальные opt-in/runtime/ресурсы/квоты и до forward сохраняет зашифрованный baseline. Ошибка snapshot запрещает исполнение. Legacy0.7 продолжает health/диагностику, но новые мутации ему не выдаются.
3. После выполнения дождитесь результата. «Снимок готов» означает доступность baseline объявленных ресурсов, а не успех forward. После ошибки forward отдельный откат тоже возможен; для unknown сначала нужна внешняя сверка отсутствия процесса.
4. Выберите «Откатить задачу» либо «Откатить группу задач». Это только подготовка нового плана. Изучите исходные задачи, узлы, hashes, срок и охват; затем отдельно подтвердите анти-скрипт.
5. В группе восстановление идёт в обратном порядке на каждой машине; другие машины независимы в пределах5/20. Read-only шаги явно отмечаются как не требующие восстановления, неподходящий изменяющий шаг не пропускается молча.
6. Проверьте отдельный итог восстановления. «Восстановлено» требует совпадения всех объявленных ресурсов с baseline. Partial/conflict не являются полным успехом. Результат исходной задачи сохраняется как история и после отката не описывает текущее состояние.

| Ресурс | Покрытие и границы |
| --- | --- |
| Конфигурационный файл | Содержимое/mtime и поддержанная metadata: Windows owner/group/DACL/attributes (SACL не входит), Linux mode/owner/xattrs. Только обычные локальные одиночные файлы до8МиБ суммарно; .json/.ini/.conf/.config/.yaml/.yml/.xml/.toml/.properties/.cfg и hosts. Не журналы, исходные скрипты, каталоги, hardlinks/streams/reparse/remoteFS или собственные config/state/vault. |
| Служба | Только running/stopped существующей службы. Не память, PID, очередь работ и конфигурация. Нужны права уже имеющейся identity; Linux service provider требует root, повышения прав нет. |
| Значение реестра | Одна HKLM/HKCU value: тип, значение и существование. HKCU — профиль агента. Созданный ключ удаляется только пустым; чужие значения не удаляются. |
| Пакет ПО | Утверждённый uninstall/absence contract в каталоге. Только доказанное отсутствие → новая установка → проверенное отсутствие после удаления. Уже нужная версия — no-op без права удалить чужую установку. Другая/неизвестная версия блокирует изменение. Это не возврат всех эффектов установщика. |

> Восстановление произвольной ОС после произвольного скрипта не гарантируется. Оператор обязан объявить все затрагиваемые объекты и учитывать окно других администраторов. Перед откатом текущее состояние сравнивается с captured post-state либо уже baseline; последующее изменение даёт conflict без перезаписи. Неподдерживаемый или непроверяемый запрос отклоняется.

Capsule хранится только на узле: Windows DPAPI, Linux AES-GCM с0700/0600, срок7дней, до100capsules/1ГиБ. В SQL/metadata backup — только typed pointer, hashes, receipt и lineage; путей/исходного кода/baseline bytes нет. Approved package uninstall/absence/version-probe contract — узкое исключение только внутри зашифрованного node capsule, чтобы undo работал после потери server RAM. Полный stdout/журналы/command forward и постпроверка по-прежнему RAM.

Перезапуск сервера не повторяет forward. Отдельный откат после рестарта возможен только с прежней identity и действующим capsule/ключом на узле. Потеря/истечение/corruption дают unavailable; не удаляйте state/vault для обхода ошибки. Смена учётной записи процесса может сделать DPAPI capsule недоступным.

Для администратора каталога: config/packages.example.json содержит незапускаемый пример recovery.uninstall_argv/absence_argv/absence_expected_output/timeouts. Замените все placeholders, проверьте отсутствие любой версии семейства приложения (не только нового MSI GUID), запрет перезагрузки и успешное удаление на одноразовом стенде. Задайте PSLC_PACKAGE_CATALOG защищённым путём; обычная поставка использует пустой каталог. Изменение каталога инвалидирует неподходящие планы, включая uninstall исходного manifest. Между шагами undo drift проверяется повторно; для внешних писателей согласуйте окно работ — это компенсация, а не транзакция всей ОС.

> Финальная native0.8 проверена standalone на Windows и в одноразовом Linux-контейнере: временный конфигурационный файл восстановлен, повторный откат идемпотентен, встроенный интерпретатор не требует Python/Node/PowerShell. Identity прежнего health-only узла и выключенные разрешения сохранены. Установка SCM/systemd, корпоративная подпись и реальные службы/реестр требуют отдельной приёмки на согласованных узлах.

## Устранение типовых проблем

| Симптом | Проверить и сделать |
| --- | --- |
| Не открывается UI | Процесс API, /healthz, правильный127.0.0.1:8787, занятость порта, frontend/dist. Не открывать listener в сеть для обхода локальной ошибки. |
| Агент offline | Доступность server из сети узла, DNS/SAN/CA, текущий config/state, credential и service identity; дата/время. Не отключать TLS и не удалять identity. |
| 401 / вход перестал работать | Время сессии, смена пароля/прав/disable, правильный контур. Войти заново. Bootstrap не сбрасывает существующего admin. |
| 403 | Роль плюс область устройства/*, текущие права, owner задачи и CSRF. Не выдавать всем admin для обхода. |
| Модель401/403/404 | Правильный HTTPS base URL, API key с правами API, точный доступный model ID. Повторно загрузить список, не публиковать ключ. |
| CPU-модель долго отвечает | Статус runtime/файла/hash/очереди, свободная RAM, CPU и размер контекста. Не путать очередь LLM с5/20 лимитами исполнения. |
| Задача unknown | Не повторять команду; сверить эффект на выбранном узле, выполнить предусмотренное reconcile. Cancel не undo. |
| Конфликт revision настроек/УЗ | Перечитать данные и применить намеренное изменение к новой ревизии; не перезаписывать чужую правку вслепую. |
| Повреждён preferences/secret | Изменения блокируются, автоматического сброса нет. Остановить сервис и восстановить доверенную отдельную config-копию. Для нового secret identity ввести ключ заново. |
| Нет результатов discovery | Правильный локальный private CIDR/фильтр/согласованные порты; отсутствие ответа не доказывает отсутствие машины. Подключить известный узел вручную. |

Для сопровождения фиксируйте версию, время, ID задачи/узла, типизированный error code и краткий эффект. Не прикладывайте ключи, passwords, исходные журналы или полный вывод команды в GitHub issues/письма.

## Планировщик: промпты и согласованные задания

Откройте «Планировщик». Расписание принадлежит сотруднику, сохраняется на паузе и включается отдельным согласием по точному обзору. Выход из браузера не останавливает согласованное правило: при каждом запуске проверяется действующая локальная учётная запись, роль и область устройств.

1. Нажмите «Новое расписание», задайте короткое название. Выберите режим: предложение плана моделью, фиксированное состояние, сбор ошибок или точный скрипт.
2. Для утреннего сбора ошибок выберите ежедневно,07:00,Europe/Moscow и «Все пользовательские ПК». Серверы, неизвестный тип и демо из этой группы исключены.
3. Для Windows будут читаться System и Application за последние24 часа, до100 событий. Для Linux укажите точную unit.service. На сервере и локальном агенте должна быть отдельно включена диагностика.
4. Для скрипта выберите конкретные узлы одной ОС. Укажите runtime/код/тайм-аут, отдельную постпроверку с точным ожидаемым выводом и все восстанавливаемые ресурсы. Для мутаций нужен native0.8/protocol1 и оба независимых допуска команд.
5. Сохраните правило. Просмотрите код, проверку, coverage анти-скрипта и список ID. Сохранение и просмотр ничего не запускают. Скрипт с неготовым узлом включить нельзя.
6. Поставьте галочку согласия и нажмите «Подтвердить и включить». Новые машины после этого не добавляются в автоматический охват: требуется повторный обзор/согласие.
7. «Запустить сейчас» использует тот же шаблон и проверки. Прежний pending/active/unknown запуск блокирует перекрытие. В истории видны допущенные и исключённые узлы, фактический исход и доступный временный план.
8. Для режима «Промпт → план» каждое исполнение требует нового точного решения. Расписание разрешает лишь подготовку предложения; LLM не наследует право на произвольные команды.
9. При необходимости откройте выполненный изменяющий шаг и отдельно подготовьте/подтвердите «Откатить задачу». Отмена/пауза расписания не возвращает систему в прежнее состояние.

> Ежедневный/недельный/разовый календарь хранит собственную IANA zone. Неделя с понедельника. Настройка часового пояса интерфейса не меняет существующее расписание. При DST повторяющийся час запускается один раз, отсутствующее время пропускается. После остановки API пропущенный срок отмечается без догоняющего запуска; автоматического retry/rollback нет.

Промпт, скрипт, код постпроверки и ресурсный контракт сохраняются только как явно заданный зашифрованный server-local шаблон. SQL содержит имя правила, календарь, ID, hash, согласие и краткие исходы. Исходные журналы/полный stdout и свободный диалог не сохраняются. UI показывает до100 последних записей за30 дней; минимальная lineage связанных задач остаётся в операционных метаданных.

Работа ограничена5 обработчиками расписаний,5 активными шагами сеанса,20 удалёнными заданиями на весь парк и одним active/unknown на узел. Offline устройство может не получить очередь до TTL плана; это явно показывается, автоматический повтор исходного действия не создаётся. Unknown требует внешней сверки завершения процесса.

## Эксплуатация и восстановление расписаний

Шаблоны по умолчанию находятся в .local/schedules отдельно от SQL. Windows: DPAPI текущей service identity и ACL владельца/SYSTEM. Linux: AES-GCM и master.key с0700/0600. Не копируйте расшифрованные шаблоны, ключи и .local в GitHub/общедоступные архивы. Смена service account или потеря ключа делает шаблон недоступным; система закрывает выполнение и не сбрасывает защиту.

1. Перед обновлением остановите новые работы и сделайте штатный metadata backup. Зафиксируйте active/unknown; не выдавайте незавершённое за успешное.
2. Для резервирования шаблонов отдельно сохраните защищённый .local/schedules с наследованием согласованных ACL и ключа/identity. Такая копия является конфиденциальным операционным материалом; metadata CLI её не включает.
3. При metadata restore все правила остаются на паузе, согласие и следующий срок очищены. Незавершённые задачи не исполняются повторно. Даже при наличии vault владелец должен заново проверить правило, календарь/цели/код и включить его.
4. После обычного рестарта будущие согласованные правила продолжаются; просроченный интервал отмечается missed, claimed/planning без готового workflow — interrupted, запущенное действие — unknown по прежним lease правилам.
5. При отзыве operator-роли, scope или отключении УЗ новые выдачи закрываются. Аудитор видит только разрешённые метаданные; чужой код/промпт не открывается. Администратор может отозвать УЗ/допуски устройства через штатные разделы, не читая чужой шаблон.

> Один API process, один scheduler clock; несколько workers/HA не поддержаны. Работайте с корректными часами ОС. Не включайте произвольные scheduled scripts под расширенными привилегиями: service account определяет доступ, поднятие прав автоматически не выполняется. Baseline покрывает только объявленные ресурсы; SCM/systemd/registry и корпоративные пакеты требуют отдельной приёмки.
