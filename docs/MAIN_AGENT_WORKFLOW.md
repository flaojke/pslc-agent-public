# Работа из «Основного раздела»

Один запрос → просмотр всего плана → подтверждение → последовательное исполнение → проверка каждого постусловия. Пока нет допуска production и реального model endpoint. Модель предлагает данные, сервер проверяет права/цели/каталог; подтверждает человек.

## Без подключённой модели

Источник плана явно обозначен «Локальные правила». Поддерживается строгая грамматика, а не произвольное понимание языка:

- `Проверь состояние узла pc-01` — точное имя или полный ID, при совпадающих именах нужен ID.
- `Установи tool версии 1.2.3 на pc-01` — только утверждённые ID/версия каталога и отдельное право установки.
- Явная команда с отдельной проверкой (обе исполняются и входят в подтверждение):

```text
Выполни python на pc-01:
print('hello')
Проверка python:
print('ready')
Ожидается:
ready
```

Runtime: python, node, powershell, cmd. Без модели один такой запрос даёт один шаг. Неоднозначный/неподдержанный запрос требует нового полного запроса в том же поле.

## С подключённой моделью

Используются существующие PSLC_MODEL_URL/MODEL_ID/MODEL_TOKEN. OpenAI-compatible `/chat/completions` должен вернуть строгий JSON по переданной схеме: plan/clarification/unsupported. План — 1–5 последовательных health/command/install шагов. Полный свободный ответ не исполняется; неправильная схема или upstream failure закрывают допуск без переключения на другую модель. Реальный Qwen/Gemma контракт требует проверки выбранного endpoint; тесты используют явно отмеченный HTTP fixture.

Реестр/каталог передаются ограниченными метаданными, credentials и исходные журналы в контекст не добавляются. Содержание запроса/контекста всё равно недоверенное; никакой текст не меняет права или обязательность решения.

## Границы доказательства

Health проверяет типизированные метрики, установка — точную версию, команда — только согласованное точное постусловие. Совпавший `print` доказывает работу процесса проверки; он не удостоверяет восстановление сервиса. Оператор должен оценить пригодность проверки по задаче. Проверочный код также способен менять состояние; он виден в плане и требует тех же прав. OS sandbox не реализован.
## API, решения и восстановление

- `POST /api/agent/requests`: request_id, session_id, question. Повтор того же ID/содержимого возвращает ту же цепочку; другое содержимое — conflict. Уточнение не создаёт заданий.
- `GET /api/workflows`: только безопасная metadata история. `GET /api/workflows/{id}` и явная подготовка запроса возвращают ещё живой RAM preview. После reload UI не восстанавливает код/промпт; для исполнения нужен новый явно просмотренный план.
- `POST /api/workflows/{id}/decision`: approve + hash всего плана; одно решение атомарно допускает все шаги. Прямое решение дочерней задачи запрещено. До подтверждения даже health не выдаётся.
- `POST /api/workflows/{id}/cancel`: запрещает новые шаги; уже выданное действие отображается по факту. Сверка unknown выполняется прежним task reconciliation API после внешней проверки; остановленная цепочка не возобновляется.

По умолчанию план/код доступны 300 секунд, сырой вывод — 120 секунд. План действует на весь оставшийся набор шагов; при истечении невыданные шаги истекают. Следующий шаг допускается после verified/already_installed; ошибка, необходимость reboot и unknown останавливают цепочку. Два действия команды (основное и проверка) выполняются внутри одного удалённого задания, оба bounded, lease покрывает суммарные timeout с запасом.

В БД добавляются workflows/workflow_steps как additive таблицы schema v2. В них нет промптов, кода, ожидаемых строк или ответа модели. Хранятся ID/хеши/порядок/типизированные факты; старые credentials/права не меняются. Pending планы после рестарта истекают; active становится unknown. Поздний исходный lease может уточнить факт шага, но не возобновляет цепочку. Качество проверки зависит от доверенного агента и пригодности постусловия; аппаратная аттестация не реализована.
