# Расследование инцидентов

Из «Основного раздела»: `Расследуй ошибки на pc-01 за последние 60 минут`. Для Linux добавьте `служба nginx.service`. Имя/полный ID должны однозначно определять узел. Без модели это явно обозначенный local_rules запрос; произвольное понимание текста не имитируется.

Перед сбором видны UTC-интервал, источник, лимиты и права процесса. Требуется подтверждение всего плана и отдельное разрешение диагностики. Investigation последний шаг: анализ не запускает исправления автоматически. Windows читает только Critical/Error/Warning из Application/System; Linux — конкретную systemd service через journalctl в доступных процессу системных журналах.

## Допуск

Новое подключение: `python -m agent --state .local/diagnostic-agent.json --enroll --allow-diagnostics`. При каждом следующем запуске нужен `--allow-diagnostics`. Существующая identity не расширяется скрыто; новое право в schema v3 у всех старых узлов выключено. Допуск команд/установок независим. Самостоятельного повышения прав/смены конфигурации журналов нет.

## Ограничения сбора

Интервал ≤24 ч в пределах последних 7 дней, ≤100 событий (по умолчанию 50), суммарно ≤64 KiB/30 с чтения с отдельным bounded завершением процесса. Сообщения ограничены 512 символами; недостающий контекст обозначается. Пустое успешное чтение, недоступность, timeout, parse error и лимиты различаются. Видимость ограничена текущей учётной записью, это не аудит всех журналов машины.

## Источники реализации

[Get-WinEvent — Microsoft](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.diagnostics/get-winevent?view=powershell-5.1): фильтрация времени/каналов и MaxEvents. [journalctl — systemd](https://www.freedesktop.org/software/systemd/man/latest/journalctl): фильтрация unit/интервала/priority, JSON. Используются фиксированные read-only argv/скрипт без shell и без записи исходных временных файлов.
## Результат и данные

`verified` для расследования означает проверенный сбор. Причина остаётся `unconfirmed`. Сохраняются scope, покрытие, количество/уровни, event/record IDs, время и opaque ref. Сообщения, provider и исходный journal cursor не сохраняются. Модель может дать только неподтверждённые категории low/medium с известными refs; explanation/next_checks временные. Пустое окно не подтверждает исправность всего узла.

После подтверждения сбор и анализ удерживают общий слот 5/20 и сериализацию узла. Анализ имеет отдельные состояния, один вызов и глобальный semaphore 5, 30-секундный HTTP timeout. Насыщение даёт capacity_limited без бесконечных retry. Ненастроенная модель даёт not_configured, пустые наблюдения — insufficient_evidence. Частичный сбор отмечается и не считается verified.

API оператора: `GET /api/tasks/{id}/investigation` возвращает metadata и ещё живой временный анализ; `POST /api/tasks/{id}/investigation/cancel` подавляет последующую публикацию и удаляет RAM cache. Запрос, уже переданный модели, может завершиться на upstream. Список workflow содержит только metadata. Duplicate result не запускает второй анализ; pending/analyzing после restart становится context_lost. При истечении RAM — expired без скрытого повторного сбора.

Исходные данные/свободный текст модели живут до output_ttl (по умолчанию 120 с) в ограниченной RAM. Никакого логирования HTTP body или SQL payload. Для OS swap/dumps и upstream logging требуется отдельная эксплуатационная проверка. Версия модели/policy и typed гипотезы сохраняются; это не восстановление полного старого контекста. Реальные Linux/корпоративная модель/контролируемый fault case A02 ещё требуют отдельного стенда.

HTTP-анализ: timeout 30 с на сетевую операцию и budget 30 с, проверяемый при получении headers/chunks. Это запрещает бесконечное продолжение потока малыми порциями; текущая блокирующая операция ограничена собственным timeout. Жёсткий wall-clock deadline для DNS/внешней инфраструктуры не заявляется. Linux timestamp переводится из целых микросекунд без потери точности через float.
